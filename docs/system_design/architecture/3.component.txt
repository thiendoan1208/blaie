C4 LEVEL 3 - COMPONENT DIAGRAMS

Purpose
-------
This document contains the current implementation snapshot followed by the target MVP V1 component model.

Current implementation note (2026-07-26)
----------------------------------------

The backend currently runs as one deployable Spring Boot modular monolith. API, outbox publication, Redis Stream
worker, job recovery, observability and retention schedulers can be enabled independently through configuration,
but they are not separate codebases.

Implemented top-level modules:

- auth: identity/session lifecycle, local auth, Google OAuth, verification, password reset and account credentials.
- authz: regular-user permission enrichment and permission-plus-ownership decisions.
- capture: text Capture/Inbox API, durable workflow, Redis transport, AI classification and admin job operations.
- audit: privacy-safe access audit recording and admin audit query.
- retention: scheduled bounded cleanup for completed jobs/outbox rows, expired idempotency keys and audit events.
- configuration: application-wide Spring Security filter-chain composition.
- core: shared request/error/cursor/rate-limit/security/observability primitives without business ownership.

Implemented protected-request order:

  RequestContextFilter
    -> AuthRequestFilter
    -> AuthorizationContextFilter
    -> AuditAccessFilter
    -> RateLimitFilter
    -> EmailVerificationRequiredFilter
    -> Controller/Application service

Implemented text Capture path:

  Web cookie + CSRF + Idempotency-Key
    -> CaptureService permission check
    -> owner-scoped PostgreSQL capture/job/outbox transaction
    -> Spring Modulith outbox listener
    -> Redis Stream identifier message
    -> generation/lease-fenced worker
    -> content and PII policy
    -> AI provider adapter
    -> PostgreSQL Capture/Inbox terminal result

PostgreSQL is authoritative. Redis is at-least-once wake-up transport and does not carry raw Capture text.
Voice/audio and image ingestion, object storage and their processors are target components, not implemented
components. Tasks, Calendar, Reminders and Information currently exist as navigation/category concepts; their
standalone CRUD modules are not implemented.

Target-model scope
------------------

The diagrams below zoom into the intended Backend API and AI Processing Worker responsibilities. They show
modules/components and responsibilities, not classes/interfaces. Entries for voice, image, object storage,
notifications and standalone item-management views describe future scope.

Auth Module
- Handles signup, login, logout and user identity.

Authorization Layer
- Ensures users can only access their own data.
- Separates normal user permissions from admin permissions.

Capture Module
- Core V1 component.
- Accepts text/image/audio capture requests.
- Validates basic input.
- Saves item with processing status pending.
- Calls File Upload Module if files are included.
- Calls Processing Job Publisher.
- Returns response quickly without waiting for AI.

File Upload Module
- Coordinates image/audio upload.
- Stores file references.

Item Management Module
- Handles item detail, manual edits, category changes, metadata updates, archive/delete
  and review status.
- Manual user edits must override AI suggestions.

Inbox/View Query Module
- Provides read models for Inbox, Tasks, Calendar events, Reminders and
  Information items.

Search & Tag Module
- Supports basic search and tag filtering in V1.

Reminder Module
- Manages reminder state.
- Prepares notification requests.

Admin Module
- Allows admin to inspect processing jobs, retry failed jobs, view metrics and audit
  admin actions.

Processing Job Publisher
- Creates background processing jobs after capture or retry request.

Repository Layer
- Data access boundary for PostgreSQL.

Object Storage Adapter
- Encapsulates file storage access.
- Keeps backend business logic independent from a specific storage provider.

Job Consumer
- Reads pending jobs from the queue.
- Starts background processing.

Processing Status Manager
- Updates item/job status:
  - pending
  - processing
  - completed
  - failed

Processing Orchestrator
- Chooses pipeline based on source type:
  - text
  - image
  - voice/audio

Text Processor
- Prepares text input for classification and metadata extraction.

Image Processor
- Extracts useful text or meaning from image input using OCR and/or image understanding.

Audio Processor
- Transcribes voice/audio input before classification.

AI Provider Adapter
- Encapsulates calls to external AI provider.
- Makes future provider/model changes easier.

Classification Component
- Classifies item into exactly one V1 category:
  - task
  - calendar_event
  - reminder
  - information

Metadata Extraction Component
- Extracts title, summary, due date, reminder time, event start/end time, priority, tags,
  confidence and reason.

Result Writer
- Persists AI output to PostgreSQL.
- Preserves original input.
- Must not overwrite user-edited fields unless user explicitly requests reprocessing.

Retry & Error Handler
- Handles failed AI/OCR/transcription jobs.
- Stores technical failure reason for admin debugging.

Notification Dispatcher
- Sends reminder notifications when needed and when permission/platform support exists.


Component design principles
---------------------------

- Capture path must be short and fast.
- AI path must be asynchronous and retryable.
- User data ownership must be checked in backend, not only in frontend.
- Manual edits must win over AI suggestions.
- Original input and AI output should be stored separately.
- Admin tooling should inspect job status and errors without exposing user content unless
  explicitly required for debugging.
